# Wallet data retrieval service

## Локальный запуск

1. Клонируйте репозиторий 
```
$ git clone https://github.com/dasegos/walletscanner-tz.git
```
2. Перейдите в папку `/core`:
```
$ cd walletscanner/core
```
3. Создайте в ней папку `/settings`:
```
$ mkdir settings
```
4. Внутри создайте файл `.env` (можно дать любое название, необязательно `.env.development` или `.env.deployment`):
- для *macos*:
```
$ nano <название файла>
```
- для *windows*:
```
$ notepad <название файла>
```
5. Вставьте в файл окружения значения следующих обязательных переменных:
```
POSTGRES_LOCAL_PORT=5432
POSTGRES_LOCAL_HOST=127.0.0.1 (postgres при запуске из докера)
POSTGRES_LOCAL_DATABASE=...
POSTGRES_LOCAL_USERNAME=...
POSTGRES_LOCAL_PASSWORD=...

REDIS_LOCAL_PORT=6379                                   
REDIS_LOCAL_HOST=127.0.0.1 (redis при запуске из докера)
REDIS_LOCAL_PASSWORD=...
```
6. Поменяйте путь к файлу окружения в `config.py` на ваш путь:
```
ENV_DEVELOPMENT_FILE_PATH = Path(__file__).resolve().parent / "settings" / ".env.development" # ЗДЕСЬ!
ENV_DEPLOYMENT_FILE_PATH = Path(__file__).resolve().parent / "settings" / ".env.deployment"


class ConfigBase(BaseSettings): 
    model_config = SettingsConfigDict( 
        env_file=ENV_DEPLOYMENT_FILE_PATH, # ЗДЕСЬ!
        env_file_encoding="utf-8", 
        extra="ignore" 
    )
```
7. Установите зависимости: 
- для *macos*:
```
$ pip3 install -r requirements.txt
```
- для *windows*:
```
$ pip install -r requirements.txt
```
8. **[Опционально]** Установите `poetry` (для удобства), если его еще нет:
```
$ curl -sSL https://install.python-poetry.org | python3 -
```
9. **[Опционально]** Если на 8-м шагу вы установили `poetry`, то запустите приложение командой:
```
$ poetry run python3 -m walletscanner.main   
```
10. **[Опционально]** Если на 8-м шагу вы НЕ устанавливали `poetry`, то запустите приложение с помощью `uvicorn`:
```
$ uvicorn walletscanner.main:app --host 0.0.0.0 --port 8888
```

>***Приложение должно запуститься!***

## Объяснение некоторых архитектурных решений:

### Модели базы данных (postgres/crud.py)

**1.** Уникальность события в блокчейне определяется хэшем транзакции и индексом лога. Согласно контракту pUSD стандарта ERC-20, на любую транзакцию, которая меняет «денежный» баланс кошелька, генерируется событие `Transfer`. Согласно контракту Conditional Tokens стандарта ERC-1155, на транзакции по переводу акций генерируются события `TransferSingle` или `TransferBatch`. Последнее является совмещением переводов нескольких акций одновременно и создано для экономии газа. Так как в базе данных для каждого токена из пакетного события `TransferBatch` создается отдельная запись, для определения уникальности транзакции дополнительно задействован `asset_id` — то есть ID токена Polymarket (`positionId`).
```
# Transaction uniqueness based on hash, log index within the block, and position ID (applicable to ERC-1155 Batch)
__table_args__ = (
    UniqueConstraint("transaction_hash", "log_index", "asset_id", name="uq_tx_hash_log_index_pos_id"),
)
```
**2.** Так как адрес кошелька в сетях EVM представляет собой нечувствительную к регистру последовательность букв и цифр, в качестве типа данных в базе используется `CITEXT`. Это гарантирует, что поиск и фильтрация по адресу (например, `WHERE from_address = '0xAbC...'`) будут успешно отрабатывать независимо от того, в каком регистре передан аргумент в запросе.

Тем не менее, на уровне приложения (через валидаторы SQLAlchemy) все адреса кошельков принудительно приводятся к нижнему регистру (lowercase) перед сохранением.   
Это сделано ради:
- **Единообразия данных (Data Consistency):** Внешние сервисы, API-интеграции и фронтенд получают адреса в строго предсказуемом формате, что исключает ошибки сравнения строк на стороне клиентов.
- **Двойной защиты:** Валидатор `@validates` в Python-коде работает только при стандартном сохранении объектов ORM. При использовании сырых SQL-запросов (execute) или массовой вставки (bulk_insert) валидатор игнорируется. В таких сценариях тип CITEXT на стороне PostgreSQL подстраховывает систему, предотвращая появление дубликатов из-за разницы в регистре букв.


>**[WARNING!] Важное примечание:** Принудительное приведение к нижнему регистру удаляет контрольную сумму адреса (EIP-55 Checksum). В таблице сохраняется только очищенное значение длиной строго 42 символа (включая префикс `0x`).

**3.** К одному адресу кошелька пользователя может быть привязано множество различных балансов (pUSD, Conditional Tokens, а в перспективе - нативная валюта POL). Для токенов стандарта ERC-1155 уникальность внутри кошелька определяется их идентификатором `asset_id` (`positionId`).
Однако такие активы, как стейблкоин pUSD (стандарт ERC-20) и нативная валюта Polygon (POL), не имеют этого идентификатора, поэтому в поле `asset_id` для них сохраняется значение None (NULL).
Чтобы база данных могла однозначно различать эти балансы и корректно масштабироваться, уникальность записи в таблице CoinBalance задается составным уникальным индексом `uq_wallet_asset_type_asset_id`, который включает в себя три поля: `wallet_address` + `asset_type` + `asset_id`. 

```
__table_args__ = (
    Index(
        "uq_wallet_asset_type_asset_id",
        "wallet_address", "asset_type", "asset_id",
        unique=True,
        postgresql_nulls_not_distinct=True
    ),
)
```
**4.** Таблица `ScanState` была спроектирована для отслеживания статуса индексации блокчейна и для предотвращения возвращения неполного набора логов (если база данных упадет во время записи этого большого набора логов).

### Перечисления базы данных (postgres/enums.py)

#### Иерархия и классификация событий
На базовом уровне блокчейна система оперирует стандартными событиями смарт-контрактов. Чтобы превратить их в понятную бизнес-логику, мы разделяем их на логические подмножества (уровни транзакций):  

**1. Уровень ERC-20 (Transfer):**  
Множество всех высокоуровневых событий Transfer разбивается на три непересекающихся подмножества бизнес-операций: снятие средств, ввод средств и рыночный перевод (`WITHDRAW`,`DEPOSIT`, `TRADE` соответственно).  
- В подмножество `WITHDRAW` попадают логи, где адрес получателя равен «нулевому адресу».
- В подмножество `DEPOSIT` — где адрес отправителя равен «нулевому адресу».
- Подмножество `TRADE` включает транзакции, где ни один из адресов не является нулевым.  

**2. Уровень ERC-1155 (TransferSingle и TransferBatch):**  
Множество логов пакетных и одиночных переводов акций разбивается на четыре подмножества бизнес-операций: разделение, слияние, выплата и торговля позициями (`SPLIT`, `MERGE`, `REDEEM`, `TRADE` соответственно).
- В подмножестве `SPLIT` адрес отправителя равен «нулевому адресу».
- В подмножествах `MERGE` и `REDEEM` адреса получателей равны «нулевому адресу» (их разделение происходит на следующем уровне логики с помощью анализа дополнительных логов транзакции).
- В подмножестве `TRADE` нулевые адреса отсутствуют.

#### Матрица применимости активов:
Бизнес-операции `SPLIT`, `MERGE` и `REDEEM` строго ограничены подмножеством токенов позиций (ERC-1155). Операции `WITHDRAW` и `DEPOSIT` применимы только к расчетному стейблкоину (pUSD). Операция `TRADE` является сквозной и может происходить в обеих группах активов.

```
class TransactionType(str, Enum):
    TRADE     = "TRADE"     # Transfer/TransferSingle/TransferBatch; _from ≠ 0x0, _to ≠ 0x0 
    DEPOSIT   = "DEPOSIT"   # Transfer; _from = 0x0, _to ≠ 0x0
    WITHDRAW  = "WITHDRAW"  # Transfer; _from ≠ 0x0, _to = 0x0
    SPLIT     = "SPLIT"     # TransferSingle/TransferBatch; _from = 0x0, _to ≠ 0x0
    MERGE     = "MERGE"     # TransferSingle/TransferBatch; _from ≠ 0x0, _to = 0x0
    REDEEM    = "REDEEM"    # TransferSingle/TransferBatch; _from ≠ 0x0, _to = 0x0


class AssetType(str, Enum):
    PUSD  = "PUSD"  # pUSD on https://polymarket.com
    SHARE = "SHARE" # YES/NO tokens
    # available for expansion ...
```

### Сервис индексации блокчейна (services/aioweb3)
В классе `AsyncWeb3Client` сервиса индексации блокчейна отдельного внимания заслуживают методы `_process_log()`, `_calculate_lost_token_asset_id()`, `get_wallet_creation_block()`.

#### Получение блока создания кошелька (get_wallet_creation_block)
Для восстановления баланса кошелька необходимо пройтись по всем блокам, начиная с блока, в котором был создан данный кошелек. Получение блока создания кошелька реализовано в методе `get_wallet_creation_block`. До того как пользователь зарегистрировался на Polymarket и фабрика создала для него кошелек, этот адрес в сети был абсолютно пуст. В момент деплоя контракта по этому адресу навсегда записывается его байткод (compiled code). Метод ищет самый первый блок в истории сети, где по заданному адресу функция `eth_get_code` возвращает непустую строку байт. Для оптимизации он использует алгоритм бинарного поиска.

#### Обработка логов и унифицирование их вида (_process_log)
При получении сырого лога от RPC-ноды, приложение должно обработать его и привести к виду, в котором он в дальнейшем будет добавлен в базу данных. В методе `_process_log` происходит разбор лога и определение его к определенной категории (по `asset_type`, `transaction_type`). Используя ABI контрактов (pUSD и Conditional Tokens), метод парсит поля `topics` и `data` сырого лога. Извлекаются базовые параметры: `from`, `to`, `amount` (для ERC-20) или `from`, `to`, `id`/`ids`, `value`/`values` (для ERC-1155), и прочие. Если пойман лог `TransferBatch`, метод берет параллельные массивы `ids` и `values` и в цикле генерирует для каждого элемента массива отдельный независимый объект транзакции, подставляя для каждого свой `asset_id`. В этом же методе происходит разделение видов транзакций `MERGE` и `REDEEM`.

#### Расчет идентификатора проигравших позиций (_calculate_lost_token_asset_id)
**Назначение:** восстановление идентификатора (`asset_id` / `positionId`) проигравших позиций на основе криптографических правил Conditional Token Framework (CTF) от Gnosis.

**Бизнес-логика в расчете балансов:**
когда рынок на Polymarket завершается (разрешается; происходит событие `PayoutRedemption`), одна из акций принимает цену, а противоположная полностью обесценивается. Проигравшие токены физически остаются на адресах пользователей в блокчейне. Для экономии газа для них не генерируется событие сжигания токенов. Чтобы при вычислении текущих балансов не включать обесценившиеся позиции в итоговую выборку, этот метод динамически воссоздает `asset_id` проигравших акций. Это позволяет отфильтровать и отсечь «мертвые» активы на уровне запросов к базе данных.

**Пошаговый алгоритм и математика вычисления:**  
Метод в точности воспроизводит логику функций `getCollectionId` и `getPositionId` смарт-контракта CTF:  

**1. Подготовка входных данных:**
- строка `condition_id` (уникальный хэш рынка) очищается от префикса `0x` и конвертируется в массив байт (bytes).
- Инициализируется родительский идентификатор коллекции `parent_collection_id` как 32 нулевых байта (`bytes(32)`), поскольку система парсит рынок верхнего уровня.
- `outcome_index_mask` принимает битовую маску проигравшего исхода (`indexSet`), указывающую на конкретный слот исхода.

**2. Вычисление `collection_id`:**  
Параметры `parent_collection_id`, `condition_id` и `outcome_index_mask` упаковываются в байтовую последовательность (encode) согласно типам данных Solidity [bytes32, bytes32, uint256]. На основе полученного батча вычисляется хэш.

**3. Вычисление `position_id` (конечного `asset_id`):**  
Из конфигурационного словаря CONTRACTS извлекается адрес контракта токена обеспечения pUSD. Адрес обеспечения и ранее вычисленный `collection_id` упаковываются (encode) в соответствии с типами [address, bytes32]. Далее рассчитывается итоговый идентификатор токена ERC-1155.

**4. Форматирование результата:**  
Полученный хэш-массив `position_id` переводится из байтового представления в целочисленное и возвращается как объект типа `Decimal` для полной совместимости с полем `Numeric(78, 0)` таблицы транзакций и балансов.
